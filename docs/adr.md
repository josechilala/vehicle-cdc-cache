# ADR 001: CDC projection and cache consistency

**Status:** Accepted

**Date:** 2026-11-13

## Context

The read model joins two independently consumed CDC topics. PostgreSQL log
positions describe database change order, while position `recorded_at` and
producer-assigned vehicle versions describe business ordering. Neither a Kafka
offset nor an LSN alone is a unique, cross-topic event order. Replays and
at-least-once delivery must converge to the same cache.

## Decision

### Ordering and versions

- Each vehicle transition carries a positive `state_version BIGINT` assigned
  by its authoritative producer when the business transition is created,
  before database delivery. It is not generated by PostgreSQL and is not
  derived from `state_updated_at`, LSN, or Kafka offset. Valid transitions for
  one vehicle have unique, increasing versions; retries keep the same version
  and payload.
- VehicleWriter's deterministic scenario assigns `1, 2, 3, ...` in intended
  business-transition order before dispatch. Delaying or retrying a transition
  preserves its original version; a late version 2 cannot be relabeled version
  4 just because it is written after version 3.
- Encode positive state versions as canonical decimal strings in Lua. Compare
  by digit count and then bytewise lexical order; do not convert 64-bit values
  to Lua floating-point numbers.
- Normal VehicleWriter updates include
  `WHERE state_version < incoming_version`, preserving the operational row
  against stale deliveries. Equal-version identical retries are no-ops;
  equal-version conflicting payloads are explicit errors.
- A separate deterministic fault-injection operation deliberately bypasses
  the normal condition and persists a lower version so Debezium emits stale
  CDC. This can temporarily regress the row. The projector keeps the greatest
  version and ignores the stale event. A subsequent snapshot of that regressed
  row cannot recover the overwritten higher version; replay requires the
  retained complete CDC history.
  Equal-version, equal-payload retries are no-ops; equal-version conflicting
  payloads are explicit writer/projection errors.
- A vehicle row candidate is ordered by `state_version`. A physical delete's
  Debezium `before` row supplies the last stored version; deletion is a
  terminal marker that dominates every row event because IDs are never
  recreated. No database-generated update counter can recover business order
  if a stale transition is written last; the producer-supplied version and
  projection max rule are the required contract.
- PostgreSQL `timestamptz` supports microseconds. Position `recorded_at` is
  normalized to fixed-width UTC `YYYY-MM-DDTHH:mm:ss.ffffffZ`, restricted to
  AD years 0001-9999, then compared bytewise. Equal times are ordered by the
  canonical lowercase UUID string `position_id`, also bytewise. Thus both
  tuple elements preserve precision and have deterministic ordering.
- Exact position insert retries reuse the same UUID and payload. On a
  PostgreSQL primary-key conflict the writer compares the persisted row:
  identical content is an idempotent no-op; different content is rejected.
  Distinct UUIDs with identical timestamp and coordinates are distinct
  position events; the greater UUID wins the equal-time tie. Replayed CDC
  records with the same tuple and value are no-ops. A conflicting value at an
  identical winning tuple is an invariant violation and is not committed.
- Treat `source.lsn`, Debezium transaction metadata (`txId` and
  `total_order` when enabled), and Kafka `(topic, partition, offset)` as
  database/delivery cursors for diagnostics, recovery, and duplicate
  identification—not as business timestamps. LSN values can be shared by
  records in a transaction; Kafka offsets from different topics/partitions
  are not comparable.

### Idempotency and cache writes

- Use at-least-once consumption with Kafka auto-commit disabled and sequential
  processing within each partition.
- Apply each validated event through one atomic Lua operation that compares
  and merges only its per-vehicle hash. A tombstone is a no-op. Commit its
  Kafka offset only after the cache operation succeeds. A crash between write
  and commit safely
  redelivers the event. A failed script is not committed.
- After the atomic projection succeeds, retry the commit of that same record
  for a bounded set of known transient coordinator, timeout, and transport
  errors. Do not reapply the projection during commit retry. Before every
  attempt, verify that the partition remains assigned. Lost ownership,
  exhausted retries, and permanent commit errors stop the Worker; Kafka may
  redeliver the already-projected record, which is safe because projection
  and progress advancement are idempotent. On rebalance, stop dispatch for
  revoked partitions and never commit a record after ownership is lost.
  Process each partition sequentially; do not queue unbounded work or commit
  past an unfinished record.
- Invalid/unparseable CDC is a visible poison record: log/alert and stop the
  affected processing loop without committing past it. No dead-letter-and-skip
  policy is adopted because that would silently omit projection state.
- Compare state and position independently in the Lua script. This makes their
  merge commutative across topic arrival order. Repeated candidates with the
  same version/key are no-ops.
- Keep projection fields and ordering metadata in the same Valkey vehicle
  hash so the conditional update and visible value are atomic. Also keep a
  per-consumer-group Valkey progress hash with one processed-next-offset field
  per topic/partition. The same Lua script advances that cursor for every
  successful record, including tombstones. This cursor is needed to detect a
  full cache loss against existing Kafka commits; it does not detect partial
  vehicle-key loss and is not used as business ordering.
- At partition assignment, require each Valkey cursor to be at least as high
  as the Kafka committed next offset. A cursor ahead of the Kafka commit is
  allowed because a crash may occur after the atomic cache write and before
  offset commit. Missing or lagging cursor with a nonzero commit fails closed.
  On every partition assignment, require both topics to have the configured
  partition count and every partition's earliest offset to equal the retained
  replay baseline. Verify committed offsets against retained ranges; a group
  without a commit explicitly seeks to the configured baseline. Configure
  Kafka offset reset to error so missing/out-of-range offsets cannot trigger
  an implicit earliest seek. These checks do not flush Valkey or reset offsets.

### Valkey model and race handling

- Key: `vehicle:{<vehicle-id>}`.
- Hash fields: `vehicle_seen`, `is_deleted`, `state_present`, `state`,
  `state_version`, `delete_state_version`, `state_updated_at`,
  `position_seen`, `position_id`, `lat`, `lng`, and `recorded_at`.
- A position arriving first creates a partial hash (`vehicle_seen=0`); readers
  treat it as pending/unknown rather than as an active vehicle. Later vehicle
  state merges without discarding the winning position.
- A normal state entry has `vehicle_seen=1`, `is_deleted=0`,
  `state_present=1`, `state`, and its `state_version`. A delete has
  `vehicle_seen=1`, `is_deleted=1`, `state_present=0`, `position_seen=0`,
  and `delete_state_version` copied from its `before` row. It has no `state`,
  `state_updated_at`, `position_id`, `lat`, `lng`, or `recorded_at`. This is
  the canonical deleted representation; readers never expose it as active.
- Delete is sticky for the lifetime of the ID. All later row events are
  ignored; all position fields are cleared by delete and later position events
  are ignored. Processing positions before or after delete yields the same
  deleted hash with no visible state or position.
- `DECOMMISSIONED` is an ordinary non-deleted vehicle state (`is_deleted=0`,
  `state_present=1`). Debezium `op=d` is the physical-row deletion event.
  The following Kafka null-valued tombstone is only a transport/compaction
  marker; it is ignored and cannot erase the versioned cache marker.
- Snapshot read (`op=r`) is a candidate at its stored business version.
  Debezium's consistent initial snapshot boundary precedes streaming changes.
  A late-processed snapshot cannot overwrite a higher `state_version`; position
  candidates follow the same event-time tuple for snapshot and streaming.
- Normal mock-writer state updates are conditional on a higher business
  version. A separate, explicitly named deterministic fault-injection
  operation deliberately persists a lower version to produce stale CDC and
  demonstrate projector ordering. This can temporarily regress the PostgreSQL
  row. If a later new snapshot is taken after that regression, it contains only
  the stale row and cannot recover the overwritten higher version; replay
  correctness is guaranteed only from the retained complete CDC history that
  includes the higher event.

### Replay and recovery

- Keep both CDC topics append-only and un-compacted. Their retention must
  preserve every record from the declared cache/capture baseline for the
  required recovery period; this challenge uses unlimited time retention
  and requires storage monitoring. If the earliest offset has advanced beyond
  that baseline, complete equality cannot be claimed. A new snapshot cannot
  restore historical deletes.
- Record each topic/partition's initial beginning offset as a required replay
  baseline in durable deployment configuration before capture starts. Query
  Kafka beginning offsets for every
  partition before clearing anything. They must still equal the configured
  baseline; if retention has advanced any beginning offset, fail closed.
  Otherwise stop the Worker, clear only `vehicle:*`, and start a fresh
  consumer group. With no committed offsets, the Worker explicitly seeks
  every partition to the configured retained baseline. A group whose progress
  was cleared must not be restarted with its old Kafka commits: use a fresh
  group or deliberately reset and verify those commits first.
  Topics/partition counts are immutable for this baseline. Do not rely on
  `auto.offset.reset` for an existing group.
- Cache loss/rebuild recovery is offline in challenge scope: readers may see
  partial data while replay runs. Zero-downtime generation swap is not
  supported.
- Partial loss of individual vehicle keys while progress metadata remains is
  not detected or repaired automatically. Supported recovery is an
  operator-driven offline full replay from complete retained history after
  verifying the baseline and clearing projection and progress data.
- Logical equality compares the sorted vehicle IDs and every projection field
  and comparison marker (`vehicle_seen`, deletion/state-presence flags,
  state value/version/timestamp, delete version, position tuple and
  coordinates). Kafka consumer offsets are checked separately at the replay
  baseline; they are not part of cache equality. Valkey encoding and ephemeral
  process state are excluded.

### End-to-end validation

- `just e2e` rebuilds the solution and recreates only the `vehicle-cache`
  namespace before running fixed deterministic fixture IDs. It never creates
  or deletes the selected Kubernetes cluster. Recreating the namespace also
  resets its PostgreSQL, Kafka, Debezium snapshot, and Valkey volumes, so the
  fixed fixture and baseline can be replayed reproducibly.
- Run the existing Worker locally, with temporary port-forwards to the
  namespace's PostgreSQL and Valkey services and Kafka's external listener.
  Kafka keeps its internal listener for in-cluster clients and advertises
  `127.0.0.1:19092` on the external listener so a host-side Kafka client can
  follow broker metadata through the port-forward. This is a local-development
  trade-off; the listener is not an external production endpoint.
- Use a dedicated `vehicle-cache-e2e` consumer group. First project the
  position-before-vehicle fixture, restart the Worker, then write vehicle
  transitions and post-delete position. Wait until Valkey partition cursors
  equal Kafka's stable end offsets before asserting the canonical hashes.
- To test duplicate delivery, retain the hashes and start a distinct fresh
  consumer group that explicitly seeks to the retained baseline. For full
  replay, verify all topic partitions still begin at offset zero, clear only
  `vehicle:*`, and start another fresh group. Compare every sorted hash field
  against the pre-replay projection. This avoids changing committed offsets
  with the Kafka group administration CLI. Cleanup stops the Worker and
  temporary port-forwards; the namespace remains for inspection.

Infrastructure readiness, PostgreSQL logical publication, Kafka topic
baselines, connector health, and all 26 unit/integration tests passed against
the active Valkey service. The live Worker recovered from the observed
coordinator commit failure with the bounded same-record retry. Restart,
duplicate redelivery from offset zero, and an actual rebalance were exercised;
the six topic/partition progress cursors reached their observed end offsets,
and the canonical cache remained equal. A separate fresh-group replay also
reached offset zero without changing the existing cache.

The latest clean `just e2e` passed all required scenarios with the single
internal offsets-topic partition configuration. Infrastructure snapshot/stream
readiness, deterministic writer-to-cache assertions, Worker restart, duplicate
delivery, and cache-cleared full replay from offset 0 all passed. The rebuilt
canonical cache was identical to the pre-replay cache. This completes the
required end-to-end validation for the accepted decision.

## Alternatives rejected

- A Worker database lookup to fill gaps violates CDC-only projection and makes
  replay dependent on mutable source state.
- Blind `SET`, client-side read/modify/write, and delete-on-tombstone can lose
  concurrent updates or resurrect stale data.
- Comparing all events by `recorded_at` is invalid for vehicle state; comparing
  all events by LSN ignores position business time and LSN ties.
- Assigning an incrementing version on each database write is insufficient:
  if a stale business update arrives last, it receives the greatest write
  counter. A source-assigned business version and projection comparison are
  required.
- Ordering state only by `state_updated_at` cannot resolve equal timestamps
  and relies on clock/order semantics that the challenge does not guarantee.
- Physical cache deletion loses a durable delete marker and can permit a late
  position to appear active.
- Kafka compacted position topics can discard a position with a lower
  `recorded_at` that was inserted after the true winner, breaking replay.
- The source's initial snapshot cannot reveal vehicle deletions or a higher
  business version overwritten by a stale update before CDC capture began.
  The local namespace starts with empty CDC topics/cache and one fixed
  infrastructure canary row (`00000000-0000-4000-8000-000000000001`) at
  version 1. Readiness requires observing its
  snapshot record and a version-2 streaming update before application writers
  start. `just down` deletes only the project namespace and its PVCs, resetting
  the canary, offsets, and source for the next run. Pre-baseline history is
  outside the supported view.

## Consequences and open questions

- An authoritative producer must assign unique increasing state versions per
  vehicle. The challenge does not define such an upstream contract; the mock
  writer makes it explicit. If IDs are ever reused, add a generation/epoch
  before implementation.
- Normal mock source updates reject lower versions. Only the explicit
  fault-injection scenario can leave PostgreSQL temporarily stale; it exists
  to exercise CDC ordering and is not a production source-update policy.
- Phase 03 implements the finite coordinated fixture and continuous writer
  modes. The finite fixture uses stable IDs and must run against a fresh source
  and CDC baseline; the writer does not orchestrate a reset or E2E replay.
  Exact position duplicate retries are idempotent, while conflicting content
  for an existing position ID fails explicitly.
- Phase 04 implements the CDC parser, single sequential Kafka consumer,
  conditional Lua projection, per-partition progress cursor, and startup
  guards. Valkey script behavior passed 7 live integration tests; fresh-group
  Kafka assignment and baseline validation were exercised against the active
  broker. The latest clean E2E also verified offset commits, full projection,
  restart, duplicate delivery, and identical cache-cleared replay from offset 0.
- Position winners are event-time maxima, not necessarily latest DB insert.
  Exact retries reuse the same UUID and are no-ops; distinct equal-time IDs
  have deterministic but business-arbitrary UUID ordering. This policy must be
  accepted by product stakeholders.
- Retention baselines, partitioning, source-table key configuration, and
  snapshot/stream readiness passed clean E2E validation. Continued retention
  of complete history remains an operational requirement.
- Complete Valkey loss is rejected at restart when committed Kafka offsets
  exist but the progress hash is missing. Loss of individual vehicle keys
  while progress remains is not automatically detected. Operators must use
  Valkey persistence and health signals, then run the offline Kafka replay
  procedure after suspected loss.
- A production-grade zero-downtime replay needs a separate namespace and
  atomic reader cutover; that is deliberately not part of this initial design.
